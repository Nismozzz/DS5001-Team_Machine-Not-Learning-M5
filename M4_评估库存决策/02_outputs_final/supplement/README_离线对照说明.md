# 离线补充对照：层级调和可用性与下单粒度

本目录是模块 04 的补充件，不改动任何正式产物（本包 `02_outputs_final` 的十七项数值保持原样）。
生成脚本三个：`01_code/make_period_pinball.py`（累计层 pinball，约 5 分钟）、`01_code/make_hierarchy_offline.py`（层级核验与下单粒度，约 15 秒）、`01_code/check_bottom_up_call.py`（实调模块 03 接口，约 1 分钟）；均无随机数，可逐位复算。

## 一、为什么要做

模块 03 的完整交接包到手后，需要回答三件事：调和是否真的做了、分位能不能直接接上库存仿真、
“按单品下单”与“按门店总量下单”差多少。这三件事都不需要重跑主流水线，可以离线算清。

## 三、核心结论

1. **点预测真调和**：顶层 28 天累计点预测由 1,146,624 变为 1,189,844（+3.8%），且精确等于 30,490 条叶层之和，加总误差 0。
2. **bottom_up 累计分位面板未实现加总（实现缺口）**：交付的 `bottom_up` 28 天累计分位与 `unreconciled` 逐行相同（L01/L03/L12 合计 701,523 行，0 差异）。这是 Module 3 的代码缺口，不是 bottom_up 的设计定义。
3. **35.45% 是 unreconciled 的 gap**：顶层对全叶分位求和的相对差，τ=0.50 时 2.63%、τ=0.95 时 35.45%、最大 49.81%；门店 CA_1 节点值比叶求和低 14.2%。修好 bottom_up 后 bottom_up gap 应为 0；即使修正，叶层分位之和也不等于总量分位（1.48× actual），这是分位不可加的统计限制。
4. **高层分位形状偏宽**：门店层 τ=0.95 覆盖 9–10/10（0.90–1.00），但总量是真实需求的 1.45–1.50 倍；τ=0.50 仅覆盖 2/10（0.20）。总量层方向相反：单一总量节点 τ=0.95 只有真实需求的 0.96–0.99，未被覆盖。
5. **下单粒度对照（5:1、τ=0.95、四窗口）**：单品下单成本 0.6943、填补率 0.9772；门店总量下单成本 0.8620（+24.1%）、填补率 0.9453（−3.2pp）。订货量 728 万 → 707 万，但期末库存 67.5 万 → 70.1 万。
   原因不是总量不够，而是把门店总量按点预测占比摊到单品后，热销品备多、冷门品备少。

## 四、限制

- 只有 lightgbm 在模块 02 与模块 03 两侧都有 28 天累计分位；三个基线的累计分位由模块 04 用“点预测 + 误差经验分位”自建，未纳入本对照。
- 口径 B 的分摊规则只用 SKU 点预测占比，未比较更优分摊方式，故 24.1% 是“最朴素分摊”的结果，不是该口径的下界。
- 门店层分位覆盖率为逐节点统计（10 店 × 4 窗口），样本量小，尾部 τ 仅供参考。
- 结论边界为 M5 数据集全部 30,490 条序列（CA 4 家、TX 3 家、WI 3 家门店）。

## 六、如何重跑

两个脚本不带绝对路径，按脚本位置向上查找含 `data/` 或 `M5/` 的项目根；模块 03 交接包另由环境变量指定：

```
$env:M5_ROOT   = "<项目根，含 data/ 与 M5/>"      # 可选，默认自动查找
$env:M3_HANDOFF = "<Module3_Full_Handoff_Module4>"  # 必需，找不到会明确报错退出
python 01_code\make_hierarchy_offline.py
python 01_code\check_bottom_up_call.py
```

`make_period_pinball.py` 只依赖项目根下的模块 02 交付与真值文件，同样自动定位。
